# Подключение и восстановление — 0.4.1

При первом обращении к проекту или `renga_status` сервер автоматически подключается, если в Windows ROT зарегистрирована ровно одна Renga. Он не запускает и не закрывает приложение, не открывает и не сохраняет проект. При нескольких процессах вызовите `renga_list_instances`, затем `renga_connect(processId=...)`. Исправное текущее подключение сохраняется, даже если позже появляется другое окно Renga.

Перед операцией выполняется безопасная проверка `HasProject`. Если COM-прокси устарел, сервер освобождает его и аннулирует UI-токен. Автоматически выбранный процесс можно заменить единственным доступным процессом. Явно указанный PID закреплён: при его исчезновении нужно осознанно выбрать новый PID. Пустой проект и занятость приложения не считаются разрывом связи.

`renga_disconnect` отключает автоматическое подключение до следующего `renga_connect`. Повторный `renga_connect` не разрывает исправную связь. Ошибочный PID или неудачное подключение к другому процессу не уничтожают существующее рабочее подключение.

## Занятость Renga и сообщения ошибок

COM-вызовы выполняются на STA-потоке с OLE-инициализацией, обработкой сообщений и `IMessageFilter`. Только вызов, отклонённый Renga как временно не принятый (`SERVERCALL_RETRYLATER`), повторяется COM с интервалом 100 мс в пределах 2 секунд. Вся транзакция, создание объекта, перемещение, ввод или вставка целиком автоматически **не повторяются**. При неизвестном результате записи сначала перечитайте модель.

Ожидаемые ошибки возвращаются как MCP `isError=true` с текстом причины: отсутствует процесс/проект, выбран неверный PID, Renga занята, потерян COM-прокси, неверные аргументы. Для COM-ошибок выводится HRESULT. Статус содержит `connectionMessage` и `autoConnectEnabled`; успешный запуск самого MCP ещё не доказывает доступность проекта.

Если Renga открыта, но ROT пуст, проверьте одинаковую учётную запись Windows и совместимый уровень запуска Renga и клиента MCP. Диалоги и незавершённые операции следует закончить в Renga. Принудительно завершать приложение или сервер для обычного повторного подключения не требуется.

## `{"detail":"Bad Request"}` и транспорт

Этот сервер работает через **stdio**, без HTTP-порта, URL или HTTP-обработчика. Ответ HTTP 400 `Bad Request` не создаётся его stdio-транспортом. Сам по себе такой текст не позволяет установить причину: нужно определить, откуда он пришёл — клиент, внешний мост или удалённый сервис. Изменения 0.4.1 исправляют жизненный цикл связи с Renga, но не заявляют об устранении невоспроизведённой ошибки внешнего сервиса.

В Codex задайте локальную команду запуска в `[mcp_servers.renga]`, а не URL. После замены пути к установленной сборке перезапустите клиент, чтобы он запустил новую версию. `startup_timeout_sec = 30` и `tool_timeout_sec = 60` достаточны для проверенной локальной сборки. Не публикуйте полную конфигурацию клиента и журналы: они могут содержать личные данные.

## Что проверено

- 57 автоматических тестов: исходные операции и восстановление соединения, неоднозначность процессов, закреплённый PID, занятость, явное отключение и сохранение исправной связи при ошибке переключения.
- Живая проверка Renga Professional 9.2 / API 2.49 через stdio: первый запрос проекта без `connect`, повторный `connect`, неверный PID, явное отключение/подключение, подробные ошибки и PNG клиентской области.
- Сведения о проекте, перечень объектов и отметки уровней до и после живой проверки совпали. Остановку реального пользовательского проекта не имитировали; потеря процесса проверена на подставных COM-сессиях.

Захват окон сторонним Computer Use использует другой компонент. Исправный `renga_ui_snapshot` не доказывает исправность Windows Graphics Capture в стороннем помощнике.
